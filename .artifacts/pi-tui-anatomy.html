Anatomy of the terminal UI - nine containers, two renderers

Every line pi draws comes from one stack of Containers built in InteractiveMode. The same instances are mounted top-to-bottom on the main screen, or rearranged into a scrolling transcript and a pinned dock in fullscreen. Hover a pin or a key entry to trace a region; toggle the controls to see which regions move, appear, or empty out.

    One tree, two renderersswitchTuiMode() moves the children; it doesn't rebuild them

    Regular mode uses TuiMainScreen: the seven top-level containers are appended as children and rendered as one tall column. Lines that scroll off the top pass into the terminal's own scrollback, and the terminal keeps mouse and scrolling.

    Fullscreen mode uses TuiAltScreen and installs a layout root from createChatViewport(): a ScrollView for the document (header, resources, chat) that grows to fill the screen, above a fixed VStack dock. The editor keeps minSize: 3; the other dock parts can shrink to zero rows. Mode switching is refused while an overlay is open.

    The render contractwhat every region is made of
    
            
    
              
    
                Each container above holds Components from
                @earendil-works/pi-tui. Components are small: they turn a width into
                lines, and the TUI does the rest.
              
    
            
    
          
    
          
    
            
    
              
    render(width) → string[]
    
              
    
                One string per terminal row. Every line must fit the width, measured with
                visibleWidth() rather than string length because of ANSI escapes and
                wide characters.
              
    
            
    
            
    
              
    invalidate()
    
              
    
                Drops cached output. Theme changes call it everywhere, so theme colors must not stay
                baked into stored strings.
              
    
            
    
            
    
              
    tui.requestRender()
    
              
    Called after state changes. Requests are coalesced into one terminal update.
    
            
    
            
    
              
    Styles reset per line
    
              
    
                pi resets styling and hyperlinks after every line, so each rendered line reapplies
                its own colors.
              
    
            
    
            
    
              
    Focusable + CURSOR_MARKER
    
              
    
                A focused input emits the marker at its cursor; the TUI strips it and places the
                hardware cursor there so IME candidate windows appear in the right place.
              
    
            
    
            
    
              
    handleInput / handleMouse
    
              
    
                Keys go to the focused component. Mouse events are only routed in fullscreen;
                unhandled wheel events scroll the nearest ScrollView.
